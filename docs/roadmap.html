Points d'attention repérés dans le code

Petites choses relevées en lisant le dépôt. Rien de bloquant pour le Sandbox, mais mieux vaut les traiter avant d'ajouter des modules.

#OùConstatPiste
1Game::init()m_systems.start() n'est appelé qu'à la construction : les systèmes ajoutés ensuite (Physics, Collision, Script…) ne reçoivent jamais onStart.Appeler onStart dans addSystem si le jeu est déjà démarré, ou exposer un game.start() après le chargement de la scène.
2SystemManagerstd::sort n'est pas stable : l'ordre de deux systèmes de même priorité n'est pas garanti.Utiliser std::stable_sort.
3ScriptSystemonDestroy n'est appelé qu'à l'arrêt du jeu, pas à la destruction d'une entité isolée.Brancher Registry::onDestroy<Script> pour appeler onDestroy.
4Game / LooseFileLoaderLe chargeur est construit avec son chemin par défaut games/rts/assets/resources.txt, hérité du prototype RTS. Sans ce fichier, les identifiants de texture sont traités comme des chemins directs.Passer un chemin explicite, ou attendre le module assets.
5engine/ai/CMakeLists.txtContient av_module(Core …) : le nom devrait être AI (sans effet tant que le dossier n'est pas ajouté à engine/CMakeLists.txt).Renommer avant d'activer le module.
6projects/rpg/CMakeLists.txtCrée une cible nommée Sandbox sous une option AV_BUILD_RPG qui n'est pas déclarée ; le dossier n'est pas ajouté au CMake racine.Renommer la cible RPG, déclarer l'option, ajouter add_subdirectory.
7render_system.hUne fonction inline void test(Camera2d&) vide traîne en bas du fichier.La supprimer.
8Intégration continueLe dossier .github/ est présent mais vide : aucun build ni test automatique.Ajouter un workflow qui lance le preset x64-debug-no-editor puis ctest.
9TestsSeul ComponentPool est testé.Ajouter des tests pour Registry::view, la destruction différée et les collisions.
