Code de jeu

Ajouter un comportement, un composant ou un système à un projet sans toucher au moteur ni à l'éditeur, grâce à trois macros : REGISTER_BEHAVIOR, REGISTER_COMPONENT et REGISTER_SYSTEM.

Le code du jeu vit dans le projet

Le moteur fournit les briques (ECS, physique, rendu). Le code propre à un jeu — comment le joueur bouge, quels composants décrivent un ennemi, quels systèmes les font agir — se range dans le dossier du projet, sous trois formes :

behaviors/

Comportements

Une classe qui hérite de IBehavior, attachée à une entité via Script. Déclarée avec REGISTER_BEHAVIOR.

components/

Composants

Une structure de données (Health, Spin…) posée sur des entités. Déclarée avec REGISTER_COMPONENT.

systems/

Systèmes

Une classe qui parcourt des composants à chaque frame, pour toutes les entités. Déclarée avec REGISTER_SYSTEM.

Chaque macro enregistre le code dans un registre global au démarrage du programme. Ce registre est lu par l'éditeur (menus, Inspector, glisser-déposer), par le chargement des scènes (retrouver une classe à partir de son nom) et par Game (ajouter les systèmes). Résultat : déposer un fichier suffit, sans modifier le moteur, l'éditeur ni une liste quelque part.

Quand choisir quoi ?

Je veux…J'écris…Parce que…
faire bouger le joueur avec le clavierun comportementla logique ne concerne qu'une entité
donner des points de vie à plusieurs entitésun composantc'est de la donnée, partagée et sauvegardée dans la scène
faire tourner toutes les entités qui ont Spinun composant + un systèmeune même règle s'applique à beaucoup d'entités
réagir à une collision d'un ennemi précisun comportement (il peut brancher le callback onCollision du Collider2D)cas particulier d'une entité

La règle d'or de l'ECS : les données dans les composants, la logique dans les systèmes. Un comportement est pratique pour un cas unique ; dès qu'une règle concerne « toutes les entités qui ont X », préférez un système.

Les dossiers d'un projet

projects/rpg/Arborescence
projects/rpg/
├── rpg.angproj           # le projet
├── CMakeLists.txt        # inclut automatiquement les trois dossiers ci-dessous
├── main.cpp              # rpg.exe
├── rpg_scene.h           # registerRpgSystems, entrées, scène de secours
├── behaviors/            # REGISTER_BEHAVIOR   (player_behaviors.h, test.h…)
├── components/           # REGISTER_COMPONENT  (spin.h)
├── systems/              # REGISTER_SYSTEM     (spin_system.h)
├── scenes/               # main.scene, iso_demo.scene
├── prefab/               # Player.prefab…
└── assets/               # input.cfg, tilesets/…

Le CMakeLists.txt du projet liste tous les *.h et *.hpp de ces trois dossiers (file(GLOB … CONFIGURE_DEPENDS)) et en fait un en-tête généré, rpg_game_code.h, qui les inclut un par un. Cet en-tête est compilé dans rpg.exe et dans l'éditeur (cible rpg_project) : le même code est donc visible aux deux endroits.

Après avoir ajouté un fichier, recompilez. Le code est du C++ : il n'apparaît dans l'éditeur qu'après une compilation. CMake détecte tout seul les nouveaux fichiers (CONFIGURE_DEPENDS) ; lancez simplement la compilation.

REGISTER_BEHAVIOR

Un comportement est une classe qui hérite de IBehavior (voir Comportements C++). Une ligne sous la classe l'enregistre :

projects/rpg/behaviors/player_behaviors.hC++
#pragma once
#include "ecs/behavior.h"
#include "ecs/behavior_factory.h"
#include "ecs/registry.h"
#include "components/rigid_body2d.h"
#include "input/input.h"

class PlayerBehavior : public IBehavior {
public:
    PROPERTY(float, speed, 250.f)      // visible dans l'Inspector, enregistré dans la scène

    void onUpdate(Entity self, Registry& registry, float dt) override {
        auto& rb = registry.getComponent<RigidBody2D>(self);
        rb.velocity.x = Input::getAxis("Horizontal") * speed;
        rb.velocity.y = Input::getAxis("Vertical")   * speed;
    }
};

REGISTER_BEHAVIOR(PlayerBehavior)      // nom utilisé dans les fichiers .scene / .prefab

Le BehaviorFactory retient le nom de la classe, comment en créer une instance et le fichier où elle est déclarée (__FILE__). C'est ce qui permet :

  • d'enregistrer un Script dans une scène : on écrit le nom et les PROPERTY ;
  • de recharger : create("PlayerBehavior") fabrique un nouvel objet ; un nom inconnu (classe renommée ou supprimée) donne nullptr et un avertissement ;
  • de glisser un fichier .h sur une entité : namesInFile("player_behaviors.h") liste les comportements qu'il déclare (le nom du fichier est comparé sans tenir compte de la casse, pour Windows).

Un même fichier peut déclarer plusieurs comportements, et une entité peut en porter plusieurs : le composant Script contient une liste (behaviors), exécutée dans l'ordre. En C++ : script.add<PlayerBehavior>(), script.get<PlayerBehavior>(), script.remove(i), script.size().

REGISTER_COMPONENT

Un composant de jeu est une simple structure avec des valeurs par défaut. Une ligne sous la structure suffit :

projects/rpg/components/spin.hC++
#pragma once
#include "ecs/game_components.h"

struct Spin {
    float degreesPerSecond = 90.f;   // vitesse de rotation
    bool clockwise = true;
};
REGISTER_COMPONENT(Spin, FIELD(degreesPerSecond), FIELD(clockwise))

Cette ligne fait trois choses :

  1. Inspector : Ajouter un composant → Spin apparaît, avec un champ par FIELD.
  2. Sauvegarde : la scène et les prefabs enregistrent le composant sous le nom Spin, avec ses champs (via un sérialiseur créé automatiquement, addReflected).
  3. Glisser-déposer : on peut glisser spin.h sur une entité pour lui ajouter le composant.
Type du champWidget dans l'Inspector
floatnombre décimal
intnombre entier
boolcase à cocher
sf::Vector2fdeux nombres (x, y)
std::stringzone de texte

Dans le code du jeu, c'est un composant comme les autres : registry.getComponent<Spin>(e), registry.view<Spin, Transform2D>(…).

Limite. Seuls les cinq types ci-dessus sont pris en charge. Un champ de type Entity, une liste ou une énumération ne se déclare pas avec FIELD : écrivez alors un sérialiseur à la main (voir Projet & sauvegarde) ou stockez un entier / une chaîne.

REGISTER_SYSTEM

Un système hérite d'ISystem, fixe sa priority et implémente onUpdate. L'inclusion de game_systems.h apporte la macro :

projects/rpg/systems/spin_system.hC++
#pragma once
#include "game_systems.h"
#include "components/transform2d.h"
#include "../components/spin.h"

class SpinSystem : public ISystem {
public:
    SpinSystem() { priority = 3; }   // après la physique et les scripts, avant le rendu (10)

    void onUpdate(Registry& registry, float dt) override {
        registry.view<Spin, Transform2D>([&](Entity, Spin& spin, Transform2D& t) {
            const float sign = spin.clockwise ? 1.f : -1.f;
            t.rotate(sf::degrees(sign * spin.degreesPerSecond * dt));
        });
    }
};
REGISTER_SYSTEM(SpinSystem)

Chaque Game (rpg.exe comme le mode Jouer de l'éditeur) ajoute tous les systèmes enregistrés dans Game::init, après ceux du moteur. Le constructeur peut être :

ConstructeurPour…
MonSysteme()un système qui ne touche qu'au Registry
MonSysteme(Game& game)accéder au jeu (entrées : game.input(), systèmes…)
MonSysteme(sf::RenderTarget& target)dessiner (interface, effets) : l'image du jeu (game.target(), une RenderTexture que le post-process affiche ensuite dans la fenêtre)

Choisissez une priority qui place votre système au bon endroit dans la frame (voir l'ordre d'exécution) : avant 10 pour agir sur les données, après 10 pour dessiner par-dessus. Le nom du système est celui de sa classe.

Activer et désactiver des systèmes

Exécuter → Systèmes… ouvre la liste de tous les systèmes du jeu dans leur ordre d'exécution, avec leur priorité et leur origine (Moteur ou Jeu). On coche ou décoche chaque système :

  • le choix est enregistré dans le projet, section systems du .angproj ("ForceDebugSystem": false) ;
  • il est appliqué au lancement (F5, rpg.exe) grâce à game.applySystemSettings(project.systems) ;
  • il prend effet tout de suite si le jeu tourne déjà dans l'éditeur.

C'est idéal pour masquer les tracés de debug (RenderCollisionSystem, ForceDebugSystem) ou isoler un système pendant qu'on cherche un bug. Un système désactivé n'est plus appelé (onUpdate), mais reste en mémoire.

Créer du code depuis l'éditeur

Dans le panneau Project, clic droit → Créer (C++) propose Behavior…, Composant de jeu… et Système de jeu…. L'éditeur demande le nom de la classe (un nom C++ valide, sinon il refuse), crée le fichier dans le bon dossier avec un modèle commenté prêt à compiler, puis rappelle qu'il faut recompiler. Il n'y a plus qu'à le remplir.

  1. Clic droit dans Project → Créer (C++) → Behavior… (par exemple test) : un fichier behaviors/test.h apparaît avec REGISTER_BEHAVIOR(test) en bas.
  2. Écrivez le code, puis recompilez (cible AngeVaultEditor).
  3. Dans l'éditeur, deux façons de l'attacher : glisser le fichier .h sur une entité (Hierarchy, Inspector ou vue scène), ou Inspector → Ajouter un composant → Comportement → test.
  4. Ctrl+S : le nom du comportement et ses PROPERTY sont dans la scène. F5 pour l'essayer.

Pourquoi recompiler ? Le code de jeu est lié à l'éditeur (cible rpg_project). Il n'y a pas de rechargement à chaud : après chaque modification de C++, il faut reconstruire l'éditeur pour que le mode Jouer utilise la nouvelle version.

Et côté moteur ? Cette page décrit le code d'un jeu. Pour ajouter un système ou un composant au moteur lui-même (dossier engine/, utilisable par tous les jeux et par l'éditeur), voir Créer un système (côté engine) et Créer un composant (côté engine).

Créer un nouveau projet de jeu

Un nouveau projet dans l'éditeur (Fichier → Nouveau projet…) crée les fichiers de données (.angproj, assets/, scenes/), mais le code d'un projet est compilé : il appartient à un exécutable déclaré en CMake. Pour avoir un jeu avec son propre code, copiez la structure de projects/rpg (CMakeLists avec le glob des trois dossiers, main.cpp) et ajoutez-la au CMakeLists.txt racine. Le projet projects/test/test.angproj sert de projet de données vide pour essayer l'éditeur.
