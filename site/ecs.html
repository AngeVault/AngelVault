Architecture

ECS & Registry

Entités, pools de composants, vues et systèmes : le cœur du module Core, expliqué avec le code réel.

Vue d'ensemble

L'ECS d'AngeVault tient en cinq fichiers d'en-têtes dans engine/core/include/ecs/ :

FichierRôle
entity.hEntity { index, generation } et NULL_ENTITY
component_pool.hComponentPool<T> : stockage d'un type de composant en sparse set
registry.hRegistry : crée les entités, possède les pools, fournit view
system.h / system_manager.hISystem et le gestionnaire qui les trie par priorité
behavior.h / property.hComportements scriptés et macro PROPERTY (voir Comportements C++)
reflect.h / component_registry.hRéflexion des composants pour l'éditeur

Entity : un index et une génération

ecs/entity.hC++
struct Entity {
    uint32_t index = 0;
    uint32_t generation = 0;   // évite les accès à des entités mortes
    bool operator==(const Entity& o) const {
        return index == o.index && generation == o.generation;
    }
};
inline constexpr Entity NULL_ENTITY = { UINT32_MAX, 0 };

Une entité n'est rien d'autre qu'un identifiant. Quand elle est détruite, sa génération est incrémentée dans le Registry ; son index peut ensuite être réutilisé par une nouvelle entité avec une génération différente. Un ancien Entity conservé quelque part échoue donc à isValid() au lieu de pointer silencieusement vers la mauvaise entité.

Piège. Entity{} vaut {0, 0} : c'est l'entité d'index 0, pas une entité nulle. Pour exprimer « aucune entité », utilisez toujours NULL_ENTITY, comme le fait EditorContext pour la sélection.

ComponentPool : le sparse set

Chaque type de composant a son propre ComponentPool<T>, composé de trois tableaux :

  • m_dense — les composants, contigus en mémoire ;
  • m_denseToEntity — pour chaque case dense, l'index de l'entité propriétaire ;
  • m_sparse — indexé par entité, donne la case dense (ou UINT32_MAX si l'entité n'a pas ce composant).
ecs/component_pool.hC++
void remove(uint32_t entityIndex) {
    assert(has(entityIndex));

    uint32_t removedDenseIdx = m_sparse[entityIndex];
    for (auto& cb : m_onDestroy) cb(entityIndex, m_dense[removedDenseIdx]);
    uint32_t lastEntityIndex = m_denseToEntity.back();
    m_dense[removedDenseIdx] = std::move(m_dense.back());
    m_denseToEntity[removedDenseIdx] = lastEntityIndex;
    m_sparse[lastEntityIndex] = removedDenseIdx;
    m_dense.pop_back();
    m_denseToEntity.pop_back();
    m_sparse[entityIndex] = UINT32_MAX;
}

Le pool expose aussi deux listes de callbacks : onConstruct (appelé après chaque add) et onDestroy (appelé juste avant la suppression). Le cas particulier « on retire le dernier élément » est couvert par test_remove_last_element dans tests/test_component_pool.cpp.

view : itérer sur les entités qui ont tous les composants

ecs/registry.hC++
template<typename... Ts, typename Func>
void view(Func&& func)
{
    std::array<IComponentPool*, sizeof...(Ts)> pools = { &pool<Ts>()... };

    size_t smallestIdx = 0;
    for (size_t i = 1; i < pools.size(); ++i)
        if (pools[i]->size() < pools[smallestIdx]->size())
            smallestIdx = i;

    IComponentPool* primary = pools[smallestIdx];

    for (size_t i = 0; i < primary->size(); ++i) {
        uint32_t idx = primary->denseToEntity()[i];
        Entity   e = { idx, m_generations[idx] };
        if (isValid(e) && (pool<Ts>().has(idx) && ...))
            func(e, pool<Ts>().get(idx)...);
    }
}

L'astuce : view choisit le plus petit pool parmi ceux demandés et ne parcourt que celui-là, puis vérifie la présence des autres composants en O(1). Un view<RigidBody2D, Transform2D> coûte donc proportionnellement au nombre de corps rigides, pas au nombre total d'entités.

usageC++
registry.view<RigidBody2D, Transform2D>(
    [&](Entity e, RigidBody2D& rb, Transform2D& t) {
        if (rb.isStatic) return;
        t.move(rb.velocity * dt);
    });

Règles d'or pendant un view.

• Ne pas ajouter ni retirer de composant du type parcouru : le push_back peut réallouer le tableau dense, et le swap & pop déplace un élément non encore visité.

• Pour supprimer une entité, utilisez destroyEntity() : la suppression est différée en fin de frame.

• Créer des entités d'autres types de composants est sans danger (c'est ce que fait shootBall depuis un Script).

Systèmes

ecs/system.h + system_manager.hC++
struct ISystem {
    virtual ~ISystem() = default;
    virtual void onStart(Registry& registry) {}
    virtual void onUpdate(Registry& registry, float dt) = 0;
    virtual void onStop(Registry& registry) {}
    int priority = 0;
};

class SystemManager {
public:
    template<typename T, typename... Args>
    T& addSystem(Args&&... args) {
        auto sys = std::make_unique<T>(std::forward<Args>(args)...);
        T& ref = *sys;
        m_systems.push_back(std::move(sys));
        std::sort(m_systems.begin(), m_systems.end(),
            [](const auto& a, const auto& b) { return a->priority < b->priority; });
        return ref;
    }
    void start(Registry& r)           { for (auto& s : m_systems) s->onStart(r); }
    void update(Registry& r, float dt){ for (auto& s : m_systems) s->onUpdate(r, dt); }
    void stop(Registry& r)            { for (auto& s : m_systems) s->onStop(r); }
};

addSystem renvoie une référence au système créé : c'est pratique pour le configurer tout de suite, par exemple pour brancher un callback de collision (voir la recette). Le cycle de vie est onStart, onUpdate (chaque frame) puis onStop (à l'arrêt).

À savoir sur onStart. Game::init() appelle m_systems.start() une seule fois, dans le constructeur de Game. Les systèmes ajoutés ensuite (comme PhysicsSystem et CameraSystem dans loadRpgScene) ne reçoivent donc jamais onStart. Aucun système actuel ne l'utilise, mais mettez votre initialisation dans le constructeur du système tant que ce point n'est pas corrigé.

Réflexion pour l'éditeur

Deux mécanismes complémentaires permettent d'afficher des champs dans l'Inspector :

  • Comportements : la macro PROPERTY(T, nom, défaut) enregistre automatiquement un PropertyInfo (nom, type énuméré, pointeur) dans IBehavior::m_properties.
  • Composants : le Core fournit reflectComponent<T>() (spécialisation par composant) et ComponentRegistry, tandis que l'éditeur décrit ses champs affichables via componentDescriptors() (getter/setter par champ, ce qui fonctionne aussi pour les champs privés comme ceux de Transform2D). Voir Éditeur Qt.

Types supportés par PropertyInfo : float, int, bool, sf::Vector2f et std::string. Tout autre type déclenche un static_assert explicite à la compilation.
