Architecture

Modules du moteur

Tour d'horizon des sept modules actifs de engine/ et des modules prévus, avec les systèmes et composants de chacun.

Core actif

engine/core — dépend de SFML::System et glm::glm. C'est la base de tout : l'ECS (voir ECS & Registry) et les composants que presque tout le monde utilise.

  • Transform2D : position, rotation, échelle, depth, avec matrice locale mise en cache (drapeau « dirty »).
  • Transform3D : position, quaternion, échelle (glm) et getModelMatrix().
  • NameComponent : nom lisible affiché par la Hierarchy.
  • Script + ScriptSystem : comportements C++ (voir Comportements).
  • Maths (math/interpolation.h, math/easing.h) : des fonctions sans état, pour float et sf::Vector2f, dans la même veine que Mathf d'Unity.

Les outils de maths

FonctionEffet
Math::lerp(a, b, t)Point à t (0..1, borné) entre a et b ; lerpUnclamped, inverseLerp et remap complètent
Math::moveTowards(pos, cible, vitesse * dt)Avance à vitesse constante et s'arrête pile sur la cible
Math::damp(pos, cible, 10.f, dt)« Lerp avec une vitesse » : rapide puis de plus en plus lent, avec le même résultat à 30 ou à 144 FPS (dampHalfLife : réglage par demi-vie)
Math::smoothDamp(pos, cible, vel, 0.3f, dt)Ressort amorti (SmoothDamp d'Unity), sans dépassement de la cible ; la vitesse vel est conservée par l'appelant, dans ses composants
deltaAngle, lerpAngle, moveTowardsAngle, dampAngleAngles en degrés, par le chemin le plus court
angleOf, fromAngle, pingPong, repeat, length, normalize, clampLengthDivers (en SFML l'axe Y descend : angleOf({0, 1}) vaut 90°)
Ease::apply(Ease::Type::OutBack, t)Déforme un t (0..1) : 22 courbes (Linear, SmoothStep, In/Out/InOut de Quad, Cubic, Sine, Back, Bounce, Expo, Elastic…) avec f(0) = 0 et f(1) = 1
usageC++
#include "math/interpolation.h"
#include "math/easing.h"

// dans un onUpdate : suivre une cible en douceur, au même rythme à tous les framerates
pos = Math::damp(pos, cible, 8.f, dt);

// animer d'un point à un autre en dépassant un peu la cible
float t = timer / duree;                                      // 0 -> 1
pos = Math::lerp(depart, arrivee, Ease::apply(Ease::Type::OutBack, t));

Ces fonctions sont vérifiées par le test test_math (voir Démarrage & build).

Physics2D actif

engine/physics2d — dépend de Core. Deux composants (RigidBody2D, Collider2D) et deux systèmes.

PhysicsSystem (priorité 0)

Intègre le mouvement en Euler semi-implicite, une fois par frame et par corps non statique :

physics_system.hC++
dt = std::min(dt, 0.05f);                      // un gros dt ne fait pas « exploser » la simulation

if (rb.useGravity) rb.applyForce(rb.mass * gravity);   // gravity = { 0, 980 } px/s²

sf::Vector2f acceleration = rb.forceAccumulator * rb.inverseMass();   // a = F / m
rb.velocity += acceleration * dt;                                    // v += a·dt

float dragFactor = 1.0f - (rb.linearDrag * dt);                      // résistance de l'air
rb.velocity *= std::max(0.f, dragFactor);

if (rb.velocity.y > terminalVelocity) rb.velocity.y = terminalVelocity;

t.move(rb.velocity * dt);                                            // x += v·dt
rb.forceAccumulator = { 0.f, 0.f };                                  // les forces se recalculent à chaque frame
ParamètreValeur par défautRemarque
gravity{ 0, 980 }pixels/s² (9,8 m/s² × 100 px/m) ; l'axe Y pointe vers le bas
terminalVelocity200000vitesse de chute maximale
plafond de dt0.05 scodé en dur dans onUpdate

CollisionSystem (priorité 1)

  • Grille spatiale de cellules de 128 px : chaque collider est inséré dans les cellules que couvre son rayon englobant, et seuls les couples qui partagent une cellule passent au test précis.
  • Formes : Box, Circle, Ellipse, Capsule, Polygon, stockées dans un std::variant.
  • Triggers : un collider isTrigger détecte sans résoudre la physique.
  • Callback : std::function<void(const CollisionInfo&)> onCollision, appelé à chaque collision. CollisionInfo contient les deux entités, la normale, la profondeur, le point de contact et le drapeau trigger.
  • Met RigidBody2D::isGrounded à vrai quand un corps est posé sur un autre.

Particles actif

engine/particles — dépend de Core. La configuration et l'état d'exécution sont volontairement séparés en deux composants :

  • ParticleEmitter : configuration modifiable (cadence emissionRate, burstCount, forme d'émission point/rectangle/cercle, angle, vitesse, accélération, durée de vie, vitesse angulaire, graine aléatoire).
  • ParticleEmitterRuntime : état (accumulateur d'émission, particules vivantes, temps écoulé…).
  • ParticleSystem (priorité 3) et ParticleManager font vivre les particules. Un émetteur peut se détruire à la fin (destroyWhenFinished).

ParticleSystem n'est pas enregistré par défaut par Game : ajoutez-le à votre scène avec game.systems().addSystem<ParticleSystem>().

Tilemap actif

engine/tilemap — dépend de SFML::Graphics. Contient les données de la carte ; le dessin est dans Render2D.

  • TileType : None, Sand, Water, Grass, BrickPath, DirtPath, DonjonFloor, Wall, Path.
  • TileMap : width, height, tileSize (16 par défaut), couche logique value (le bit 7 = TF_SOLID, les bits 0–6 = type), couche walls, et un TileSet (variantes, animations).
  • Dual-grid : le visuel est posé sur les sommets entre quatre tuiles (VertexPiece avec un masque de 4 coins), ce qui produit des transitions de terrains propres avec très peu de textures.
  • layerOrder : ordre d'empilement des terrains, du dessous au dessus (sable, eau, herbe, chemins…).
  • Compteurs de version version, animVersion, layerVersion : le rendu ne reconstruit que ce qui a changé.
  • La carte grandit automatiquement vers les coordonnées négatives (consumeGrowOffset() donne le décalage appliqué).

Input actif

engine/input — dépend de SFML::Window. Le jeu ne lit plus les touches directement : il demande des actions nommées, comme avec l'Input Manager d'Unity. Le lien entre une action et les touches est une donnée, pas du code.

comportementC++
#include "input/input.h"

const float moveX = Input::getAxis("Horizontal");     // -1..1 : flèches, Q/D, stick gauche…
if (Input::getButtonDown("Jump")) { /* vrai à la frame où l'action démarre */ }
ÉlémentRôle
InputActionUn nom, un type (Button : enfoncé / relâché ; Axis : valeur réelle bornée à −1..1), une zone morte (0,2 par défaut, pour les manettes) et une liste de liens
InputBindingUne entrée physique reliée à une action : Key, MouseButton, MouseWheel, JoystickButton ou JoystickAxis, avec un scale (−1 pour « gauche »)
InputManagerPossède les actions et l'état de la frame. handleEvent reçoit chaque événement SFML, update() calcule l'état des actions avant les systèmes, endFrame() oublie les « Down / Up » et la molette après
Input:: (input/input.h)Façade : getAxis, getButton, getButtonDown, getButtonUp, getKey, getKeyDown, getMouseButton, mousePosition, mouseWheelDelta. Elle lit l'InputManager du Game en cours (InputManager::current()) ; sans Game (tests…), tout renvoie 0 ou faux

Les actions viennent d'un petit fichier texte, assets/input.cfg du projet, une action par bloc :

projects/rpg/assets/input.cfgShell
# [Nom] button|axis deadzone=<0..1>
#   key <Touche> [échelle] | mouse <Left|Right|Middle|Extra1|Extra2> [échelle] | wheel [échelle]
#   joybutton <manette> <bouton> [échelle] | joyaxis <manette> <X|Y|Z|R|U|V|PovX|PovY> [échelle]

[Horizontal] axis
key Left -1
key Right
key Q -1
key A -1
key D
joyaxis 0 X

Si le fichier est absent, le projet charge ses actions par défaut en C++ (defaultRpgInput dans rpg_scene.h). On le modifie dans l'éditeur, sans recompiler : Édition → Input Manager… (voir Éditeur Qt). Le RPG déclare Horizontal, Vertical, Zoom, ZoomWheel, CameraX et CameraY.

Mode embarqué. Quand le jeu est lancé seul (game.run()), Game passe lui-même les événements de la fenêtre à l'InputManager. Dans l'éditeur, c'est GameView qui les lui transmet après les avoir traduits de Qt vers SFML (qt_sfml_input) : le jeu lit donc ses touches par le même chemin dans rpg.exe et dans l'éditeur.

Render2D actif

engine/render2d — dépend de Core, Physics2D, Tilemap, Input et SFML::Graphics. Seul module qui dessine.

Geometry et RenderSystem (priorité 10)

Le composant Geometry contient un std::variant de quatre formes plus un layer :

FormeChamps
BoxDatahalfSize, style
CircleDataradius, style
PolygonDatapoints, style
SpriteDatatextureId, rect (découpe), tint

Le style regroupe fillColor, outlineColor, outlineThickness et un textureId optionnel. Chaque frame, RenderSystem collecte les entités ayant Transform2D + Geometry, les trie par layer, puis dessine chacune avec sa matrice locale.

Textures : LooseFileLoader

Les textures sont chargées à la demande et mises en cache par identifiant. L'identifiant est résolu via un fichier de correspondance id → chemin ; s'il n'y est pas, il est traité comme un chemin direct. Si le fichier est introuvable, un damier magenta/noir de 32×32 est utilisé : une texture manquante se voit tout de suite.

Caméra : Camera2d et CameraSystem (priorité −10)

Dans le jeu, la caméra est une entité : un Transform2D (sa position) et un composant Camera2d (ses réglages). Le CameraSystem, enregistré par la scène du projet, passe en premier (priorité −10) et appelle window.setView(...) : tous les systèmes de rendu qui suivent dessinent donc dans la vue de la caméra.

scène (rpg_scene.h)C++
Entity cameraEntity = registry.createEntity();
registry.addComponent<Transform2D>(cameraEntity).setPosition({ 200.f, 100.f });
auto& camera = registry.addComponent<Camera2d>(cameraEntity);
camera.setWorldBorder({ 0.f, 0.f }, { 3000.f, 3000.f });   // la vue ne sort jamais de la carte

// La caméra suit le joueur
registry.getComponent<Camera2d>(cameraEntity).setTarget(player);
  • Caméra liée (targetLock valide) : la position de la caméra est celle de la cible, à chaque frame. Si la cible est détruite, la caméra redevient libre.
  • Caméra libre (targetLock == NULL_ENTITY) : flèches pour la déplacer, + / − pour zoomer.
  • Bornes du monde : si worldMax dépasse worldMin, le zoom arrière est limité pour que la vue ne dépasse pas la carte (minZoom est recalculé à chaque frame) et clampPosition garde le centre de la vue dans la carte. Une carte plus petite que la vue est centrée.
  • Dans l'éditeur, la vue scène n'utilise pas Camera2d mais sa propre EditorCamera ; les caméras de la scène y sont simplement dessinées.

À savoir. Le CameraSystem lit encore directement sf::Keyboard (flèches, +, −) : les actions Zoom, ZoomWheel, CameraX et CameraY déclarées par le RPG ne sont pas encore utilisées. Les champs panSpeedGamepad et zoomLerpSpeed ne sont pas encore lus non plus : le zoom s'applique immédiatement. Voir la feuille de route.

Autres systèmes

  • TileMapRenderSystem (priorité 5) : dessine la tilemap ; il tient compte des compteurs de version de TileMap.
  • RenderCollisionSystem (11) et ForceDebugSystem (12) : superpositions de débogage pour voir les colliders et les forces.
  • Utilitaires : LooseFileLoader, TextureFactory, TilesetFactory, ColliderFactory.

Runtime actif

engine/runtime — dépend de Render2D, Input et SFML::Window. Contient la classe Game : voir la boucle de jeu. Elle enregistre d'office RenderSystem, RenderCollisionSystem et ForceDebugSystem, et possède l'InputManager du jeu (game.input()).
