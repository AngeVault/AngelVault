Architecture

Modules du moteur

Tour d'horizon des huit modules actifs de engine/ et des modules prévus, avec les systèmes et composants de chacun.

Core actif

engine/core — dépend de SFML::System et glm::glm. C'est la base de tout : l'ECS (voir ECS & Registry) et les composants que presque tout le monde utilise.

  • Transform2D : position, rotation, échelle, depth, avec matrice locale mise en cache (drapeau « dirty »).
  • Transform3D : position, quaternion, échelle (glm) et getModelMatrix().
  • NameComponent : nom lisible affiché par la Hierarchy.
  • Script + ScriptSystem : un composant qui porte plusieurs comportements C++ (voir Comportements).
  • PersistentId : identifiant stable (64 bits) d'une entité, qui survit à l'enregistrement. C'est lui qui relie les entités dans un fichier .scene (voir Projet & sauvegarde).
  • BehaviorFactory et GameComponentRegistry : les registres remplis par REGISTER_BEHAVIOR et REGISTER_COMPONENT (voir Code de jeu).
  • Maths (math/interpolation.h, math/easing.h) : des fonctions sans état, pour float et sf::Vector2f, dans la même veine que Mathf d'Unity.

Les outils de maths

FonctionEffet
Math::lerp(a, b, t)Point à t (0..1, borné) entre a et b ; lerpUnclamped, inverseLerp et remap complètent
Math::moveTowards(pos, cible, vitesse * dt)Avance à vitesse constante et s'arrête pile sur la cible
Math::damp(pos, cible, 10.f, dt)« Lerp avec une vitesse » : rapide puis de plus en plus lent, avec le même résultat à 30 ou à 144 FPS (dampHalfLife : réglage par demi-vie)
Math::smoothDamp(pos, cible, vel, 0.3f, dt)Ressort amorti (SmoothDamp d'Unity), sans dépassement de la cible ; la vitesse vel est conservée par l'appelant, dans ses composants
deltaAngle, lerpAngle, moveTowardsAngle, dampAngleAngles en degrés, par le chemin le plus court
angleOf, fromAngle, pingPong, repeat, length, normalize, clampLengthDivers (en SFML l'axe Y descend : angleOf({0, 1}) vaut 90°)
Ease::apply(Ease::Type::OutBack, t)Déforme un t (0..1) : 22 courbes (Linear, SmoothStep, In/Out/InOut de Quad, Cubic, Sine, Back, Bounce, Expo, Elastic…) avec f(0) = 0 et f(1) = 1
usageC++
#include "math/interpolation.h"
#include "math/easing.h"

// dans un onUpdate : suivre une cible en douceur, au même rythme à tous les framerates
pos = Math::damp(pos, cible, 8.f, dt);

// animer d'un point à un autre en dépassant un peu la cible
float t = timer / duree;                                      // 0 -> 1
pos = Math::lerp(depart, arrivee, Ease::apply(Ease::Type::OutBack, t));

Ces fonctions sont vérifiées par le test test_math (voir Démarrage & build).

Physics2D actif

engine/physics2d — dépend de Core. Deux composants (RigidBody2D, Collider2D) et deux systèmes.

PhysicsSystem (priorité 0)

Intègre le mouvement en Euler semi-implicite, une fois par frame et par corps non statique :

physics_system.hC++
dt = std::min(dt, 0.05f);                      // un gros dt ne fait pas « exploser » la simulation

if (rb.useGravity) rb.applyForce(rb.mass * gravity);   // gravity = { 0, 980 } px/s²

sf::Vector2f acceleration = rb.forceAccumulator * rb.inverseMass();   // a = F / m
rb.velocity += acceleration * dt;                                    // v += a·dt

float dragFactor = 1.0f - (rb.linearDrag * dt);                      // résistance de l'air
rb.velocity *= std::max(0.f, dragFactor);

if (rb.velocity.y > terminalVelocity) rb.velocity.y = terminalVelocity;

t.move(rb.velocity * dt);                                            // x += v·dt
rb.forceAccumulator = { 0.f, 0.f };                                  // les forces se recalculent à chaque frame
ParamètreValeur par défautRemarque
gravity{ 0, 980 }pixels/s² (9,8 m/s² × 100 px/m) ; l'axe Y pointe vers le bas
terminalVelocity200000vitesse de chute maximale
plafond de dt0.05 scodé en dur dans onUpdate

CollisionSystem (priorité 1)

  • Grille spatiale de cellules de 128 px : chaque collider est inséré dans les cellules que couvre son rayon englobant, et seuls les couples qui partagent une cellule passent au test précis.
  • Formes : Box, Circle, Ellipse, Capsule, Polygon, stockées dans un std::variant.
  • Triggers : un collider isTrigger détecte sans résoudre la physique.
  • Callback : std::function<void(const CollisionInfo&)> onCollision, appelé à chaque collision. CollisionInfo contient les deux entités, la normale, la profondeur, le point de contact et le drapeau trigger.
  • Met RigidBody2D::isGrounded à vrai quand un corps est posé sur un autre.

Particles actif

engine/particles — dépend de Core. La configuration et l'état d'exécution sont volontairement séparés en deux composants :

  • ParticleEmitter : configuration modifiable (cadence emissionRate, burstCount, forme d'émission point/rectangle/cercle, angle, vitesse, accélération, durée de vie, vitesse angulaire, graine aléatoire).
  • ParticleEmitterRuntime : état (accumulateur d'émission, particules vivantes, temps écoulé…).
  • ParticleSystem (priorité 3) et ParticleManager font vivre les particules. Un émetteur peut se détruire à la fin (destroyWhenFinished).

ParticleSystem n'est pas enregistré par défaut par Game : ajoutez-le à votre scène avec game.systems().addSystem<ParticleSystem>().

Tilemap actif

engine/tilemap — dépend de SFML::Graphics et nlohmann_json. Contient les données des cartes ; le dessin est dans Render2D. Le détail (formats, autotile, isométrique) est dans la page Tilemaps & tilesets.

  • TileMapData : une grille de cases TileCell (un entier qui désigne un tileset et une tile, ou « autotile »), une orientation (Orthogonal ou Isometric), une taille de case et la liste de ses tilesets. Elle se lit et s'écrit en JSON (fichier .map).
  • Tileset : une feuille d'images (PNG) découpée en grille, avec un mode d'autotile (None, Corners16, Edges16), un point d'ancrage, une échelle, un indicateur solid et le tri en Y (ySort). Fichier .tileset.
  • Tilemap : le composant à poser sur une entité (file, visible, data). Le Transform2D de l'entité donne la position de la carte ; une scène peut avoir zéro, une ou plusieurs cartes.
  • cellCenter, cellAt, cellCorners : conversions entre cases et coordonnées du monde, identiques en orthogonal et en isométrique.
  • version et modified : le rendu ne reconstruit que ce qui a changé.

Input actif

engine/input — dépend de SFML::Window. Le jeu ne lit plus les touches directement : il demande des actions nommées, comme avec l'Input Manager d'Unity. Le lien entre une action et les touches est une donnée, pas du code.

comportementC++
#include "input/input.h"

const float moveX = Input::getAxis("Horizontal");     // -1..1 : flèches, Q/D, stick gauche…
if (Input::getButtonDown("Jump")) { /* vrai à la frame où l'action démarre */ }
ÉlémentRôle
InputActionUn nom, un type (Button : enfoncé / relâché ; Axis : valeur réelle bornée à −1..1), une zone morte (0,2 par défaut, pour les manettes) et une liste de liens
InputBindingUne entrée physique reliée à une action : Key, MouseButton, MouseWheel, JoystickButton ou JoystickAxis, avec un scale (−1 pour « gauche »)
InputManagerPossède les actions et l'état de la frame. handleEvent reçoit chaque événement SFML, update() calcule l'état des actions avant les systèmes, endFrame() oublie les « Down / Up » et la molette après
Input:: (input/input.h)Façade : getAxis, getButton, getButtonDown, getButtonUp, getKey, getKeyDown, getMouseButton, mousePosition, mouseWheelDelta. Elle lit l'InputManager du Game en cours (InputManager::current()) ; sans Game (tests…), tout renvoie 0 ou faux

Les actions viennent d'un petit fichier texte, assets/input.cfg du projet, une action par bloc :

projects/rpg/assets/input.cfgShell
# [Nom] button|axis deadzone=<0..1>
#   key <Touche> [échelle] | mouse <Left|Right|Middle|Extra1|Extra2> [échelle] | wheel [échelle]
#   joybutton <manette> <bouton> [échelle] | joyaxis <manette> <X|Y|Z|R|U|V|PovX|PovY> [échelle]

[Horizontal] axis
key Left -1
key Right
key Q -1
key A -1
key D
joyaxis 0 X

Le chemin du fichier est donné par le projet (paths.input dans le .angproj). S'il est absent, le projet charge ses actions par défaut en C++ (defaultRpgInput). On le modifie dans l'éditeur, sans recompiler : Édition → Input Manager… (voir Éditeur Qt). Le RPG déclare Horizontal, Vertical, Zoom, ZoomWheel, CameraX et CameraY. Le CameraSystem lit Horizontal, Vertical et ZoomWheel.

Mode embarqué. Quand le jeu est lancé seul (game.run()), Game passe lui-même les événements de la fenêtre à l'InputManager. Dans l'éditeur, c'est GameView qui les lui transmet après les avoir traduits de Qt vers SFML (qt_sfml_input) : le jeu lit donc ses touches par le même chemin dans rpg.exe et dans l'éditeur.

Render2D actif

engine/render2d — dépend de Core, Physics2D, Tilemap, Input et SFML::Graphics. Seul module qui dessine. La caméra y vit aussi : Camera2d, CameraFollow, CameraBounds, CameraControl, CameraShake et leurs systèmes.

Geometry et RenderSystem (priorité 10)

Le composant Geometry contient un std::variant de quatre formes plus un layer :

FormeChamps
BoxDatahalfSize, style
CircleDataradius, style
PolygonDatapoints, style
SpriteDatatextureId, rect (découpe), tint

Le style regroupe fillColor, outlineColor, outlineThickness et un textureId optionnel. Chaque frame, RenderSystem collecte les entités ayant Transform2D + Geometry, les trie par layer puis par Y (le point de tri d'une entité est le bas de sa forme, ses « pieds »), puis dessine chacune avec sa matrice locale. Le tri est stable (std::stable_sort).

Tri en Y : arbres, murs et personnages

Les tiles d'un tileset marqué ySort ne sont pas dessinées avec le sol : le TilemapRenderSystem (priorité 8) les dépose dans une file, la YSortQueue (une par fenêtre). Le RenderSystem (priorité 10) les mélange aux entités de la couche YSortQueue::kEntityLayer (1, celle des personnages) : le joueur passe donc derrière un arbre quand il est au-dessus de lui, et devant quand il est en dessous. Sans RenderSystem sur la cible, la carte dessine ces tiles tout de suite.

Textures : LooseFileLoader

Les textures sont chargées à la demande et mises en cache par identifiant. L'identifiant est résolu via un fichier de correspondance id → chemin ; s'il n'y est pas, il est traité comme un chemin direct. Si le fichier est introuvable, un damier magenta/noir de 32×32 est utilisé : une texture manquante se voit tout de suite.

Caméra : Camera2d et ses composants

Dans le jeu, la caméra est une entité : un Transform2D (sa position) et un composant Camera2d (zoom, rotation, priorité). Tout le reste est optionnel et vit dans des composants séparés, chacun avec son système. Le projet les enregistre d'un coup avec registerCameraSystems(game.systems(), game.target()) (systems/camera_systems.h), qui ajoute les cinq systèmes dans le bon ordre :

PrioritéSystèmeComposantRôle
−1CameraControlSystemCameraControlpan et zoom (clavier, manette, molette) via les actions de l'Input Manager
4CameraFollowSystemCameraFollowsuit une cible : zone morte, avance (look-ahead), ressort amorti ; après la physique et les scripts
5CameraBoundsSystemCameraBoundsgarde la vue dans une zone : zoom mini et position
6CameraShakeSystemCameraShaketremblement par « trauma », ajouté à la vue de la frame
7CameraSystemCamera2dvue finale : caméra active + effets + fondu entre caméras

Le CameraSystem dessine dans l'image du jeu (game.target(), une sf::RenderTexture) et non plus directement dans la fenêtre : tous les systèmes de rendu qui suivent (priorité ≥ 8) dessinent dans la vue de la caméra, puis Game copie l'image à l'écran à travers le post-process.

en code (ou dans l'Inspector)C++
Entity cameraEntity = registry.createEntity();
registry.addComponent<Transform2D>(cameraEntity).setPosition({ 200.f, 100.f });
registry.addComponent<Camera2d>(cameraEntity).setZoom(1.5f);

registry.addComponent<CameraBounds>(cameraEntity).set({ 0.f, 0.f }, { 3000.f, 3000.f });   // la vue ne sort jamais de la carte

// Plus court, avec les raccourcis de utils/camera_utils.h :
Camera::follow(registry, cameraEntity, player);   // ajoute CameraFollow si besoin
Camera::shake(registry, 0.5f);                    // fait trembler la caméra affichée
  • Plusieurs caméras. La caméra affichée est la plus prioritaire (priority) parmi les actives (CameraSystem::activeCamera(registry)). Quand elle change, la vue passe de l'ancienne à la nouvelle en blendTime secondes (0 = coupure).
  • Suivi. CameraFollow remplace l'ancienne « caméra liée » : smoothTime règle le rattrapage, deadZone laisse la cible bouger sans faire bouger la caméra, lookAhead anticipe la vitesse du RigidBody2D de la cible (lissée par lookAheadTime). Si la cible est détruite, la caméra redevient libre.
  • Pas de déplacement manuel en suivant. CameraControl ne déplace pas une caméra qui a une cible valide ; le zoom marche toujours.
  • Bornes. Avec CameraBounds valide (max > min), le zoom arrière est limité (limitZoom) pour que la vue ne dépasse pas la zone, et la position est bornée.
  • Écran de référence. CameraSystem::setReferenceSize(taille) fixe la taille d'écran que « voient » les caméras (0×0 = la fenêtre, le cas de rpg.exe). L'éditeur y met la taille du projet : en jeu, la caméra montre la même zone que son cadre dans la vue scène, quelle que soit la taille du panneau, avec des bandes sur les côtés si le format diffère (CameraSystem::letterbox).
  • Souris ↔ monde. Camera::screenToWorld(Input::mousePosition()) et Camera::worldToScreen(point) utilisent la dernière vue appliquée (CameraSystem::currentView()) : pratique pour un clic sur un bouton ou un viseur.
  • Dans l'éditeur, la vue scène n'utilise pas Camera2d mais sa propre EditorCamera ; les caméras de la scène y sont simplement dessinées. Une caméra qui suit une entité y est placée sur elle et ne peut plus être déplacée à la main.

Entrées de la caméra. Le CameraControlSystem ne lit pas sf::Keyboard : il passe par les actions nommées, donc par le fichier input.cfg (CameraX, CameraY, Zoom, ZoomWheel par défaut ; les noms se changent dans le composant). Ajoutez ces actions à votre input.cfg si vous utilisez CameraControl. Les tests sans fenêtre de ces systèmes sont dans tests/test_camera.cpp.

Autres systèmes

  • TilemapRenderSystem (priorité 8) : dessine les entités qui portent un composant Tilemap. En isométrique, il dessine de l'arrière vers l'avant et ne traite que la zone visible. TilemapRenderer::draw et drawGhost (aperçu du pinceau) sont aussi utilisés par l'éditeur.
  • RenderCollisionSystem (11) et ForceDebugSystem (12) : superpositions de débogage pour voir les colliders et les forces.
  • Utilitaires : LooseFileLoader, TextureFactory, ColliderFactory, YSortQueue.

Scene actif

engine/scene — dépend de Core, Physics2D, Render2D et nlohmann_json. C'est ce qui permet d'enregistrer et recharger : le même code lit les fichiers pour l'éditeur et pour rpg.exe. Tout est détaillé dans Projet & sauvegarde.

FichierContenu
scene_io.hsaveScene, loadScene, sceneToString, sceneFromString, ensurePersistentIds : une scène complète en JSON
component_serializer.hSerializerRegistry : comment chaque composant s'écrit et se relit ; les composants de jeu déclarés avec REGISTER_COMPONENT y sont ajoutés tout seuls
prefab.h.prefab : un groupe d'entités réutilisable (savePrefab, instantiatePrefab)
project.hProject : le fichier .angproj (scène de départ, dossiers, fenêtre, chemin des réglages, systèmes actifs)
tilemaps.hloadTilemaps : charge les fichiers .map référencés par les composants Tilemap d'une scène

Runtime actif

engine/runtime — dépend de Render2D, Input et SFML::Window. Contient la classe Game : voir la boucle de jeu. Elle dessine dans une RenderTexture (game.target()) copiée à l'écran à travers un post-process facultatif. Elle enregistre d'office TilemapRenderSystem, RenderSystem, RenderCollisionSystem et ForceDebugSystem, puis tous les systèmes déclarés par le projet avec REGISTER_SYSTEM (game_systems.h), et possède l'InputManager du jeu (game.input()).

  • Game(taille, titre, settings) : ouvre une fenêtre réglée : taille et titre viennent de la section window du .angproj, les autres réglages d'un GameSettings.
  • GameSettings (game_settings.h) : plein écran, vsync, antialiasing (0, 2, 4, 8 ou 16), limite de FPS (ignorée avec la vsync), shader de post-process et ses réglages. Ils sont lus dans assets/settings.cfg (chemin : paths.settings du .angproj) ; fichier absent ou clé manquante : valeurs par défaut. Dans l'éditeur : Édition → Paramètres du jeu…. game.applySettings(settings) les applique en cours de route.
  • PostProcess (render/post_process.h) : un shader .frag appliqué à l'image du jeu. Il reçoit frame, resolution et time, plus ses propres réglages déclarés par un commentaire // @param <défaut> <min> <max> après l'uniform ; l'éditeur en fait des curseurs et la valeur choisie est enregistrée dans settings.cfg (shader.<nom> = valeur). Un shader qui ne compile pas est simplement désactivé, avec un message dans la console.
  • game.applySystemSettings(project.systems) : active ou désactive des systèmes par leur nom. Les noms inconnus sont ignorés.
  • game.systems() : find, setEnabled, isEnabled et list permettent de lister les systèmes dans leur ordre d'exécution (c'est ce qu'affiche Exécuter → Systèmes…).
