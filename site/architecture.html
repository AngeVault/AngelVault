Architecture

Architecture

Comment le dépôt est découpé, comment les modules dépendent les uns des autres et ce qui se passe à chaque frame.

Principes directeurs

  • Données et logique séparées. Un composant est une structure de données (RigidBody2D, Transform2D…), un système est une classe qui parcourt ces données (PhysicsSystem…). Il n'y a pas de hiérarchie d'objets de jeu.
  • Un module = un dossier = une cible CMake. Chaque sous-système de engine/ est une bibliothèque indépendante AngeVault::<Nom> avec ses propres dépendances.
  • Seul Render2D dessine. La physique, les scripts et les particules ne touchent jamais à une fenêtre : ils modifient des composants, le rendu les lit ensuite.
  • Le moteur ignore l'éditeur. L'éditeur Qt dépend du moteur, jamais l'inverse. Le même code de scène sert au jeu autonome et à l'éditeur.

La boucle de jeu

La classe Game (module Runtime) possède un Registry, un SystemManager et un InputManager. Elle s'utilise de deux façons, ce qui permet de partager le même code entre le jeu et l'éditeur :

ModeConstructeurQui fait tourner la boucle ?Utilisé par
AutonomeGame game; (fenêtre 1920×1080)game.run() : événements → clear → tick → displaySandbox.exe et rpg.exe
EmbarquéGame game(fenetre);L'appelant, en appelant game.tick(dt) à chaque frame et en lui passant les événements (game.input().handleEvent(…))GameView dans l'éditeur (F5)
engine/runtime/src/game_loop.cppC++
void Game::tick(float dt) {
    InputManager::setCurrent(&m_input);
    m_input.update();                    // état des actions pour cette frame
    m_systems.update(m_registry, dt);    // tous les systèmes, dont RenderSystem
    m_registry.flushPendingDestroys();   // les destructions demandées pendant la frame
    m_input.endFrame();                  // oublie les « Down / Up » et la molette de cette frame
}

void Game::handleEvents() {
    while (const auto event = m_window->pollEvent()) {
        m_input.handleEvent(*event);     // les actions voient chaque événement
        if (event->is<sf::Event::Closed>()) m_isRunning = false;
        // Échap quitte aussi
    }
}

void Game::run() {
    m_clock.restart();
    while (m_isRunning) {
        float dt = m_clock.restart().asSeconds();
        handleEvents();
        m_window->clear(sf::Color::Black);
        tick(dt);
        m_window->display();
    }
    stop();   // onStop de chaque système, une seule fois
}

Ordre d'exécution des systèmes

Chaque ISystem possède une priority : le SystemManager trie ses systèmes à chaque addSystem et les exécute du plus petit au plus grand.

PrioritéSystèmeModuleEnregistré par
−10CameraSystemRender2Dla scène du projet (loadRpgScene) : règle la vue de la fenêtre avant tout le reste
0PhysicsSystemPhysics2Dla scène du projet (loadSandboxScene, loadRpgScene)
1CollisionSystemPhysics2Dla scène du projet
2ScriptSystemCorela scène du projet
3ParticleSystemParticlesà ajouter explicitement (pas enregistré par défaut)
5TileMapRenderSystemRender2Dla vue tilemap de l'éditeur
10RenderSystemRender2DGame::init()
11RenderCollisionSystemRender2DGame::init() (debug des colliders)
12ForceDebugSystemRender2DGame::init() (debug des forces)

Priorités égales. Le tri utilise std::sort, qui n'est pas stable : deux systèmes de même priorité peuvent s'exécuter dans n'importe quel ordre. Donnez toujours une priorité distincte à deux systèmes dont l'ordre compte.

Entrées et ordre des systèmes. L'InputManager n'est pas un système : Game::tick le met à jour avant les systèmes (update()) et le vide après (endFrame()). Un script lit donc toujours un état cohérent pendant toute la frame, quelle que soit la priorité des systèmes.

Le système de build

Le CMakeLists.txt racine exige CMake 3.28 et C++20, puis ajoute le moteur, les projets Sandbox et RPG, l'éditeur (si Qt 6 est trouvé) et les tests. Quatre options contrôlent ce qui est construit :

OptionDéfautEffet
AV_BUILD_EDITORONConstruit l'éditeur Qt (nécessite Qt 6 ; sinon un avertissement s'affiche et seul le moteur est construit)
AV_BUILD_SANDBOXONConstruit l'exécutable Sandbox
AV_BUILD_RPGONConstruit l'exécutable rpg (lié à AngeVault::Engine, ses assets sont copiés à côté). L'éditeur en dépend s'il est construit
AV_BUILD_TESTSONConstruit et enregistre test_component_pool et test_math dans CTest
cmake/AngeVaultHelpers.cmakeCMake
# av_module(Nom DEPS <cibles...>)  ->  cible av_<Nom>, alias AngeVault::<Nom>
#   Aucun .cpp  => module 100 % header (INTERFACE)
function(av_module name)
  cmake_parse_arguments(ARG "" "" "DEPS" ${ARGN})
  file(GLOB_RECURSE srcs CONFIGURE_DEPENDS "${CMAKE_CURRENT_SOURCE_DIR}/src/*.cpp")
  if(srcs)
    add_library(av_${name} STATIC ${srcs})
    target_include_directories(av_${name} PUBLIC include)
    target_link_libraries(av_${name} PUBLIC ${ARG_DEPS})
  else()
    add_library(av_${name} INTERFACE)
    target_include_directories(av_${name} INTERFACE include)
    target_link_libraries(av_${name} INTERFACE ${ARG_DEPS})
  endif()
  add_library(AngeVault::${name} ALIAS av_${name})
endfunction()

Conséquence pratique : créer un module revient à écrire une ligne dans un CMakeLists.txt, déposer des en-têtes dans include/ et, si besoin, des sources dans src/. Voir la recette « Ajouter un module ».

Décisions d'architecture

DécisionRaison
Composants stockés en sparse setItération contiguë et rapide sur les composants, ajout/retrait en O(1), recherche par entité en O(1). Voir ECS & Registry.
Génération dans chaque EntityUne entité détruite dont l'index est réutilisé n'est plus confondue avec la nouvelle : isValid() compare les générations.
Destruction différéedestroyEntity() ne fait que mettre en file ; flushPendingDestroys() agit en fin de frame, ce qui évite d'invalider un view en cours.
Scène partagée dans sandbox_scene.h / rpg_scene.hloadRpgEntities (données) et loadRpgScene (systèmes + données) sont séparées : l'éditeur charge les entités dans son propre Registry sans lancer le jeu. L'éditeur ouvre aujourd'hui le projet RPG.
Entrées par actions nomméesUn script demande Input::getAxis("Horizontal") au lieu de lire sf::Keyboard : les touches deviennent une donnée (input.cfg) modifiable dans l'éditeur sans recompiler, et le clavier, la souris et la manette passent par le même chemin.
Caméra = entité dans le jeuCamera2d + Transform2D + CameraSystem : la caméra se règle dans l'Inspector comme n'importe quelle entité. La vue scène de l'éditeur garde sa propre EditorCamera, qui n'est jamais sauvegardée avec la scène.
EditorContext comme busAucun panneau ne parle à un autre : tous lisent/modifient le contexte et réagissent à ses signaux Qt. Voir Éditeur Qt.
Bibliothèques statiquesBUILD_SHARED_LIBS OFF : seule l'éditeur a besoin de livrer les DLL Qt (windeployqt est lancé après le build).
